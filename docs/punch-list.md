- [ ] **[ROOT-CAUSED 2026-10-01 — the undo half is real; a proposed fix was written, caught by its own test, and reverted. Fix needs upstream API work.]** [editor][P1][audit-2026-10-01] **Properties-panel "add blank row" (`MarkdownView::insertFrontmatterProperty`, `src/editor/MarkdownView.cpp:182-223`) destroys the user's undo history.** It routes a user-initiated edit through `doc->setMarkdown(...)` → `NoteDocument::setMarkdown` → `resetContent(..., Markoff::Origin::TestFixture)` (`libs/core/src/NoteDocument.cpp:114-120`), and that origin **replaces the entire CRDT buffer and clears the undo stack** (`MarkoffDocument.cpp:707-728`, comment: *"Clear the undo stack so this seed is not undoable"*). (The *load* paths are fine — `TestFixture` shares a case with `FirstOpen`. The defect is confined to this user-edit path.) **Root cause established by experiment: there is NO `Origin` that makes a full-content reset undoable on the D2 path.** `Origin::UserRevertToSaved` looks like the answer and is **not** — it pushes its mega-edit onto the **legacy** CRDT buffer, but `resetContent()` then runs `wipeD2State(); buildD2FromBytes()` *outside* the origin switch (`MarkoffDocument.cpp:743-745`), unconditionally and outside any undo transaction. Net effect: `undoD2()` **corrupts** the document rather than reverting it. A fix using that origin was written, and its regression test **caught it and it was reverted** rather than shipped. **`Origin.h`'s "pushes one mega edit so Ctrl+Z reverses it" comment is stale with respect to the D2 path — worth correcting upstream.** **Real fix needs a Markoff API for a *local* frontmatter edit that participates in D2 undo**: frontmatter lives in a `FrontmatterMap` *outside* the D2 block space, so `applyFlatEdit` cannot reach it, and the only public frontmatter methods are `frontmatterValue()` (read) and `applyRemoteFrontmatterMapOp()` (collaboration replay).
