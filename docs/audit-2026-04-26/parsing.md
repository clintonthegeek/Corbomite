Sources cross-checked: `~/bin/ObsidianRAW/.../parsing/*.js` (8 files); `libs/markoff-family/libs/markoff-parser/{src,include}`; `libs/markoff-family/libs/rapidyaml/`; `libs/storage/src/MetadataParser.cpp`; `libs/vault/src/FileManager.cpp`; `libs/core/src/LinkUtils.cpp`; `libs/bases/src/PropertyId.cpp`. ## Architecture fit (rapidyaml vs Obsidian's YAML lib; tree-sitter vs CM stream-parser)

Obsidian uses `eemeli/yaml` v2 (YAML 1.2, core schema, no anchors, `nullStr: ""`, `lineWidth: 0`). Corbomite vendors **rapidyaml (ryml)** as `libs/markoff-family/libs/rapidyaml/`, wrapped by `Markoff::YamlValue` (`libs/markoff-family/libs/markoff-parser/src/YamlValue.cpp:1-535`). Architecturally that is the right shape — a high-fidelity Tree DOM that preserves key order and node-style (quoted vs plain) — but ryml is a fundamentally **different emitter** with no compatibility knobs corresponding to `nullStr` / `lineWidth`. The wrapper goes through `ryml::emitrs_yaml<std::string>(node)` (`YamlValue.cpp:484`) with default `EmitOptions` (`libs/markoff-family/libs/rapidyaml/src/c4/yml/emit.hpp:58-90`). Trailing newlines are stripped (`YamlValue.cpp:487-489`).

For Markdown, Obsidian uses CodeMirror's stream-parser; Corbomite uses **tree-sitter-markdown + tree-sitter-markdown-inline** (`libs/markoff-family/libs/markoff-parser/src/vendor/tree-sitter-markdown/`). The grammar is patched/forked from MDeiml's tree-sitter-markdown with first-class Obsidian extensions (wiki_link, highlight, obsidian_comment, latex_block, minus_metadata frontmatter; see `tree-sitter-markdown-inline/grammar.js` lines containing `_highlight_open`, `_obsidian_comment_open`, `wiki_link`, `_latex_span_start`). The block grammar emits `minus_metadata`/`plus_metadata` nodes for the frontmatter fence (`TreeSitterParser.cpp:251`). Inline parsing is run **per-region** (`TreeSitterParser.cpp:208-217`), one parse per `inline` block, which is more precise than CodeMirror's stream model but loses the "incremental, line-stream" property Obsidian relies on for huge-doc perf — not a behaviour gap, but a perf-shape difference worth flagging.

Inside Corbomite, the `parsing/`-equivalent surface is split across three places: (1) **frontmatter extraction + YAML parse + write-back** lives in `Markoff::Document` (`Document.cpp:39-145, 376-409`); (2) **link/heading utilities** live in `libs/core/LinkUtils.{h,cpp}`; (3) **wikilink split** lives in `Markoff::parseLinktext` (`LinkTextParser.cpp:6-16`). There is **no single-file `parseFrontMatterTags/Aliases/StringArray/Entry` library**; consumers reach into `YamlValue` directly, and `MetadataParser.cpp` re-implements the tag-merge logic ad-hoc.

## Implemented (parity-equivalent)

- `getFrontMatterInfo` shape — `Document::frontmatterSpan() -> std::pair<int,int>` (`Document.cpp:167-172`) plus `frontmatter()/frontmatterRaw()` (`:157-165`) cover {`from`, `to`, `frontmatter`, `exists` (= `span.has_value()`)}. CRLF tolerant on the opening line (`Document.cpp:46`). Closing-`---` check requires preceding `\n` (`indexOf("\n---", 3)`, `:47`) — equivalent to Obsidian's `"\n" === e.charAt(n.index - 1)` invariant (`getFrontMatterInfo.js:16`).
- `frontmatterEofClose` — closing `---` at EOF without trailing newline is detected (`Document.cpp:60, 68-74`) and surfaced via `Document::frontmatterHasEofClose()`. Obsidian's `Qx = /---(\r?\n|$)/g` accepts the same shape; Corbomite matches. Test coverage: `tst_frontmatter.cpp:193-202`.
- `parseYaml` — `YamlValue::parse` (`YamlValue.cpp:497-522`). YAML 1.2 strictness is **manually re-implemented** because ryml's tag-resolution is not strictly 1.2 by default: the helpers `isYaml12Bool` (`:25-29`) and `isYaml12Null` (`:31-34`) only accept `true|True|TRUE|false|False|FALSE` and `null|Null|NULL|~|<empty>`. Crucially, **YAML-1.1-only tokens `yes/no/on/off/y/n` are kept as strings** — verified by `tst_frontmatter.cpp:142-159`. This is a critical Obsidian-compat behaviour and Corbomite has it right.
- `parseLinktext` — `Markoff::parseLinktext` (`LinkTextParser.cpp:6-16`) is a 4-line implementation that splits at the first `#` and is byte-equivalent to Obsidian's behaviour. Handles `#heading`, `Note#H1#H2`, `Note#^block`, `#heading` (path empty), and the no-subpath case. Test coverage: `tst_linktext.cpp:23-72`.
- `stripHeading` / `stripHeadingForLink` — `libs/core/src/LinkUtils.cpp:69-81` ports Obsidian's `AT` and `PT` regexes verbatim into Qt syntax (see the comments at `:11-13, 19-25` calling out the source mapping).
- `parsePropertyId` — `libs/bases/src/PropertyId.cpp:11-26` implements the Bases column-key parse. The unknown-prefix rule matches Obsidian: an unrecognised prefix returns `{Note, fullKey}` (Corbomite line 25). Direct test coverage at `libs/bases/tests/tst_yaml_schema.cpp:19-46`.
- `tags`/`tag` frontmatter merge — `MetadataParser.cpp:419-461` reads both `tags` (array or string) **and** `tag` (singular, array or string). This is *more permissive* than Obsidian's `parseFrontMatterTags`, which only matches `/^tags$/i` — see "Partial / divergent" below.
- Tree-sitter wikilink/embed extraction (`TreeSitterParser.cpp:794-826`).

## Partial / divergent

- **No `parseFrontMatterEntry/StringArray/Tags/Aliases` standalone helpers.** Spec §11 already calls these out as Missing; they remain missing. Each consumer rebuilds the logic. Concretely:
  - **MetadataParser** does a partial reimplementation that *adds* a `tag:` (singular) fallback Obsidian does **not** support (`MetadataParser.cpp:451-460`). A user with a `tag: foo` key in frontmatter would see `#foo` in Corbomite's tag index but **not** in Obsidian's. Functionally permissive, semantically divergent.
  - **MetadataParser** silently treats a string `tags: alpha, beta` as one tag (the whole string with leading `#`) instead of comma-splitting (`MetadataParser.cpp:445-449`). Obsidian's `parseFrontMatterTags` would call `parseFrontMatterStringArray`, which wraps the string in a single-element array, then `.filter(e => !!e && !e.includes(" "))` would **drop the value entirely** (because `"alpha, beta"` contains a space). So Corbomite emits `#alpha, beta` as one bogus tag where Obsidian emits nothing. **Cross-tool diff trigger.**
  - **MetadataParser** never trims tags before the space-check, never filters out tags containing spaces. Obsidian's filter `!e.includes(" ")` (`parseFrontMatterTags.js:9`) is missing.
  - **Aliases** are not parsed by MetadataParser at all. There is no `cache.aliases` populated from frontmatter; the only consumer that needs aliases (Quick Switcher, search) won't see them from Corbomite's metadata pipeline. Spec §11 also flagged this.
- **`getFrontMatterInfo` BOM / leading-blank-line tolerance.** Obsidian's `Yx = /^---(\r?\n)/g` requires the *very first* characters to be `---\r?\n` — a BOM, leading blanks, or leading whitespace makes `exists === false`. Corbomite uses `source.startsWith("---\n")` / `startsWith("---\r\n")` (`Document.cpp:46`), which is **functionally identical**: BOM (U+FEFF) at the start makes detection fail in both implementations. (No BOM-stripping anywhere — verified across vault/storage/parser sources.) This is *correct* parity but worth documenting as a known sharp edge: a vault opened in a BOM-saving editor would get its frontmatter ignored by both Obsidian and Corbomite, so neither tool corrupts the other's view.
- **`contentStart` is missing from the public Corbomite API.** `frontmatterSpan()` returns `{first, second}` = `{0, afterFm}`. Obsidian's `from` (start of YAML) and `contentStart` (start of body) are recoverable but not surfaced. Consumers wanting "start of body" call `Document::markdownContent()` which returns a *new QString* instead of an offset. For in-place splice operations this means Corbomite has to do extra string concatenation — see `withFrontmatter` below.
- **`stringifyYaml` formatting** is shaped fundamentally differently — see "Frontmatter round-trip risks" §below.
- **`extractSubpath` heading match is too loose.** `Document::extractSubpath` (`Document.cpp:274-374`) does a hyphen-to-space replace then case-folds (`:325-327`), but it does *not* call `stripHeading` (which would strip `*` `_` `[` etc.). So `#bold` would not match `## **bold**` in Corbomite, where Obsidian's `resolveSubpath` → `stripHeading` would. The companion `Corbomite::resolveSubpath` in `LinkUtils.cpp:83-198` *does* use `stripHeading` correctly, but the in-Document version (used by reading/embed code paths) is the divergent one. Two different subpath resolvers with two different rules is itself a bug.
- **Block-id matching** in `Document::extractSubpath` (`:289-296`) does `lines[i].contains(marker)` — substring match anywhere in the line — where Obsidian's `resolveSubpath` block branch consults `cache.blocks` which is populated only for genuine block-anchor positions. False positives possible if `^id` appears inside a code span or inline code.
- **Footnote def offset shift** — known limitation tracked in addendum `2026-04-15-markoff-footnote-def-offset-shift.md`. Footnote-def *removal* in `Document.cpp:94-95` shifts every subsequent tree-sitter offset against the raw source, but `MetadataParser` only compensates for the frontmatter shift (`MetadataParser.cpp:308-311`). Latent bug for any consumer that converts AST offsets back to raw bytes when footnote-defs precede the target.

## Missing

- `parseFrontMatterEntry(fm, key)` — no equivalent.
- `parseFrontMatterStringArray(fm, key)` — no equivalent. Bare-string-to-single-element-array normalisation is not centralised.
- `parseFrontMatterAliases(fm)` — no consumer reads aliases from frontmatter into a structured cache field.
- `parseFrontMatterTags(fm)` — only an inlined ad-hoc version in `MetadataParser` that diverges from Obsidian (see Partial above).
- `processFrontMatter` semantics — `FileManager::processFrontMatter` (`FileManager.cpp:124-146`) exists but it does **not** drop the `---` block when the mutator empties the map. Obsidian's `vI` checks `Object.keys(fm).length === 0` and removes the block entirely. Corbomite's path: empty map → `withFrontmatter(emptyMap)` → emits `---\n{}\n---\n` (or just `---\n\n---\n`) prepended to body, **not** stripped. Need to confirm by reading `withFrontmatter` and `YamlValue::stringify` of an empty map; either way the spec-mandated "remove block when empty" branch is not visible in Corbomite.
- **`processFrontMatter` does not enforce key-order preservation.** The Corbomite implementation rebuilds a *fresh* `YamlValue::emptyMap` and re-applies the mutated `QVariantMap` (`FileManager.cpp:140-143`). The new map's key order is **QVariantMap iteration order = lexicographic by key** (Qt Map = QMap, sorted), **not** insertion order. So every `processFrontMatter` call **reorders frontmatter keys alphabetically** on write. Obsidian explicitly preserves JS object insertion order. This is a **major round-trip stability bug** — see next section.
- **No Markdown→QString round-trip preserving CRLF.** The detection accepts `\r\n`, but the write side always emits `\n`. Same as Obsidian (spec §3 notes "CRLF preservation is lost"); Corbomite matches the Obsidian behaviour, so cross-tool LF normalisation will be uniform.
- **Comment-preservation** — ryml *can* preserve comments in its DOM but `YamlValue` does not surface them; `withFrontmatter` will discard any `#comment` lines. Same as Obsidian.

## Frontmatter round-trip risks (CRITICAL)

This is the highest-stakes section. Obsidian writes frontmatter via `eemeli/yaml` v2 with `nullStr: ""`, `lineWidth: 0`. Corbomite writes via `ryml::emitrs_yaml` with **default options**. Concrete deviations I can identify by reading the wrapper and the ryml emit headers:

1. **Key reordering (most severe).** `FileManager::processFrontMatter` (`FileManager.cpp:138-143`) round-trips through a `QVariantMap`. `QVariantMap` is `QMap<QString, QVariant>` — **sorted by key**. Therefore: every call to `processFrontMatter` rewrites the file with frontmatter keys in alphabetical order, regardless of the source order. A vault user who edits a Note's "tags" through Corbomite's properties UI will see the entire frontmatter reshuffle on save. Editing the same file in Obsidian will then *re-shuffle back* (Obsidian preserves insertion order from parse). **Diff churn on every edit, in both directions.** The spec says Obsidian's invariant is "JS object property insertion order — stable for existing keys if not deleted/re-added"; Corbomite cannot honour this without abandoning `QVariantMap` as the mutator-facing type or building an order-preserving wrapper.
2. **Null serialisation.** Obsidian: `nullStr: ""` → `key:` (with trailing space, no value). Corbomite: ryml default → `key: ~` (or `key: null` depending on ryml version). The wrapper's `setNull` (`YamlValue.cpp:391-398`) does `to_keyval(ch, keyView, {})` which emits an empty val — ryml will write this as `key: ` with no value tag. **Probably matches Obsidian's `key: ` output**, but needs a byte-exact spike to confirm. Other paths (`v.kind() == Null` from a previously-parsed `~`) would re-emit `~`. **Untested.**
3. **Quoting style for plain strings.** ryml chooses single-quoted, double-quoted, or plain based on its own heuristics; eemeli/yaml chooses double-quoted by default for strings needing quoting. A title `My: Note` in Obsidian writes as `'My: Note'` or `"My: Note"` depending on lib; ryml will pick whichever needs the least escaping. **Not byte-stable across tools** — any string requiring quoting is a churn point.
4. **List style.** Obsidian (eemeli/yaml v2 with `lineWidth: 0`) emits **block sequences** (`- foo\n- bar`) for arrays. ryml *also* defaults to block style for sequences, which matches. But a sequence Obsidian wrote as flow (`[a, b]`) and ryml later re-emits will *probably* be reformatted to block. Confirmed risk for `tags: [a, b]` (`tst_frontmatter.cpp:64-72`) — the inline-flow form would round-trip to block.
5. **Indent width.** ryml default = 2 spaces; eemeli/yaml v2 default = 2 spaces. **Match.**
6. **String values with spaces / special chars.** Obsidian's `nullStr: ""` plus its plain-scalar-resolver may emit a different escape than ryml. Worst case: Unicode strings with embedded `:` or leading `-`. No regression test exists in `tst_frontmatter.cpp` covering byte-exact emit comparison.
7. **Tags emission.** Obsidian writes tags **without** the `#` prefix (the `#` is injected at read time). Corbomite's `MetadataParser` reads tags both with and without `#` and prepends if missing (`MetadataParser.cpp:425-432`) — read parity OK. But there is no symmetric *write* logic: if a plugin or Bases call ever writes a tag string starting with `#` into frontmatter, Corbomite will store the literal `#tag` in YAML where Obsidian would have stored `tag`. **Diff trigger if any write path calls `setSeq("tags", ["#foo"])`.**
8. **`withFrontmatter` always emits `---\n` + yaml + `---\n`** (`Document.cpp:407`). Empty map → emits `---\n\n---\n` (one blank line if `stringify` on empty returns `""`). Obsidian removes the block entirely when the mutated object is empty — Corbomite leaves an empty `---/---` shell. **Diff churn for any mutation that empties frontmatter.**
9. **Trailing-newline of frontmatter body.** `YamlValue::stringify` strips trailing `\n`s (`YamlValue.cpp:487-489`), then `withFrontmatter` re-inserts a single `\n` before `---`. Obsidian's eemeli/yaml ends a `Document.toString()` with one `\n`; the wrapper code there appends `---\n`. Both produce `key: value\n---\n` so they agree.
10. **`processFrontMatter` cannot strip the frontmatter block.** Even if the mutator empties the map, Corbomite emits a present-but-empty block (see #8). Obsidian deletes it. Round-trip: a file with `---\n---\n` (`tst_frontmatter.cpp:87-93`) read by Obsidian then written would *delete* the block; Corbomite would *keep* it.
11. **CRLF closing fence.** `Document.cpp:55-58` consumes `\r` then `\n` after `\n---`, but `withFrontmatter` always writes LF. Cross-tool: both Obsidian and Corbomite normalise to LF on write — consistent.
12. **Inline `null`/`~`/empty.** `isYaml12Null` accepts the empty string (`YamlValue.cpp:33`), so `key:\n` parses as Null and `key:` parses as Null. On write, `setNull` emits empty val. Obsidian with `nullStr: ""` likewise emits empty val. **Read/write agree** — *probably* the cleanest of the round-trip pieces.

The `roundTrip` test (`tst_frontmatter.cpp:289-311`) verifies *structural* equality after one cycle but does **not** assert byte equality, so all of the above are uncovered by existing tests.

## Notable concerns / suspected bugs

1. **`processFrontMatter` reorders keys alphabetically on every save** (`FileManager.cpp:138-143`). `QVariantMap` = sorted `QMap`. This breaks Obsidian's documented insertion-order invariant and will cause diff churn on every edit. **Highest-priority fix.**
2. **`processFrontMatter` cannot remove an emptied frontmatter block** (`Document.cpp:397-409` always emits the `---/---` fence when value is non-null). Mutator that deletes all keys leaves a `---\n\n---\n` shell where Obsidian deletes the block. Suggested: `withFrontmatter` should detect `value.isMap() && value.size() == 0` and treat it as `value.isNull()`.
3. **Two different subpath resolvers with different rules.** `Markoff::Document::extractSubpath` (`Document.cpp:274-374`) uses hyphen-to-space + lowercase. `Corbomite::resolveSubpath` (`LinkUtils.cpp:83-198`) uses `stripHeading` + lowercase. The Corbomite one matches Obsidian; the Markoff one does not. They are called from different code paths — embeds and "open subpath" use the Markoff one (?), backlinks/MetadataCache use the Corbomite one. **Inconsistent results between hovering an embed and clicking a backlink.**
4. **`MetadataParser` accepts a singular `tag:` key** (`MetadataParser.cpp:451-460`) which Obsidian does not. Plugins that probe `MetadataCache.tags` will see tags from `tag:` in Corbomite but not Obsidian. Minor cross-tool semantic divergence.
5. **`MetadataParser` interprets a string-typed `tags: alpha, beta` as a single bogus tag** including the comma and space (`MetadataParser.cpp:445-449`). Obsidian's strict implementation drops it because it contains a space.
6. **No `aliases` extraction by `MetadataParser`.** Search/Quick-Switcher integration is blind to alias frontmatter. Spec §11 already flagged this; status unchanged.
7. **`extractSubpath` block-id mode does substring matching** (`Document.cpp:292`), risking false positives inside code spans / inline backticks containing `^id` text.
8. **Footnote-def offset shift latent bug** (addendum 2026-04-15). Any consumer reading raw-source offsets for headings/links/tags after a footnote-def line gets wrong bytes.
9. **`YamlValue::stringify` byte format is not pinned by any test.** The `roundTrip` test (`tst_frontmatter.cpp:289-311`) verifies structural equality after a parse-emit-parse cycle but never asserts byte equality. There is no golden-file for "this YAML mapping should serialise to exactly these bytes". A ryml version bump could silently change wire format.
10. **`Document::frontmatterRaw()` byte-faithful for the YAML body, but `YamlValue::parse` then `YamlValue::stringify` is *not* byte-faithful.** Even if all keys are preserved and unchanged, ryml's emit will normalise quoting style, list style, indentation of nested maps, and trailing newlines. A "no-op" call to `processFrontMatter` (mutator that mutates nothing) would re-write the file with normalised YAML formatting. Combined with #1, every save = full reformat.
11. **`Document::withFrontmatter` and `processFrontMatter` use UTF-8 round-trips through `QString`** which is fine for content but means a file with bytes that don't UTF-8-decode (corrupt/binary content) would not be preserved byte-exactly. Edge case.
12. **`parseLinktext` is in `Markoff::` namespace** but spec describes it as a vault-domain concept. Cross-domain consumer (`LinkResolver.cpp:104`) calls it correctly. Just a naming/location note.

**Suggested next-step priorities** (cluster-sized): (a) replace `QVariantMap` mutator surface in `processFrontMatter` with an order-preserving wrapper or direct `YamlValue` mutation; (b) add a byte-exact emit test against an Obsidian-written golden frontmatter sample; (c) consolidate tag/alias extraction into a `libs/core/FrontMatterHelpers.{h,cpp}` (the missing `parseFrontMatterTags/Aliases/StringArray/Entry` quartet) so MetadataParser's ad-hoc logic can be deleted; (d) fix the empty-map-to-stripped-block transition in `withFrontmatter`; (e) collapse the two `extractSubpath`/`resolveSubpath` implementations into one.
